# 通知与浏览器兜底先做管路，可见物留给 UI PR

用户明确 UI 改动单独开 PR。Toast、诊断包菜单、浏览器兜底打开门户页都含托盘可见物，现在实现会与后续 UI 大改冲突并返工。因此本系列只构建 Core/Service 管路：状态沿以受控代码写入 status.json，托盘消费端在 UI PR 落地。服务与托盘之间没有管道或 socket，status.json 是唯一通道，这决定了“推送”只能靠轮询差异发现。

## 通知载荷

`StatusNotification(Code, At)`：Code 取自 NotificationCodes 受控词表，文案由托盘渲染；载荷持久存在于 status.json 直到被新通知取代，托盘按 At 单调递增判断“新通知”，因此不需要持久序号。托盘重启最多重放最近一条——AuthenticationPaused 的重放是有意的（用户重新登录就应该看到暂停），其余代码的重放由 UI PR 决定是否抑制。

## 浏览器兜底

连续认证失败达阈值时服务只在 status.json 置 BrowserFallbackRequested（含冷却时间戳），不自行启动浏览器：服务运行在会话 0，启动的用户进程不可见；且凭据绝不进浏览器进程，只开页面不填表。托盘见标志后用默认浏览器打开门户页。

## Consequences

- 通知与兜底的“发生了”可离线测试；“用户看到了什么”要等 UI PR 后现场验收。
- 文案不在 Core：新增通知只加词表项，不改数据结构。
- 原始设想中的 Seq 持久序号被 At 单调比较取代：序号需要额外的持久计数器与崩溃恢复，而 At 已经随每次发布天然递增。
